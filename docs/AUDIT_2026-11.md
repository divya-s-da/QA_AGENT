# Supervised QA Product — Audit and Market Readiness (2026-11-09)

Scope: compare the OLD engine (ADK sequential pipeline) with the NEW v2 engine (parallel teams), say which is
better, find where v2 lags and why, give the fix, state the market requirement, and lay out the path to a
market-ready product. Benchmark numbers are quoted from `benchmark/results/`. Market numbers are from public
sources (listed at the end); most are vendor-authored, so treat them as directional.

---

## 1. Verdict in one line

v2 is the right engine. It already beats the old engine on every quality dimension and matches the one market
pain no competitor has solved well — **false confidence** (a "pass" on a broken app). The product is not yet
market-ready: three engineering gaps (model-slot starvation, no safe-write mode, a latent guard crash) and the
usual go-to-market gaps (hosting/security, CI/CD, pricing) stand between the current state and a sellable product.

---

## 2. Old engine vs v2 — which is better

Benchmark app: `benchmark/shoplite` — 22 planted bugs, 5 of them "T0" (money / auth / permissions / delete),
5 of them "success traps" (the app shows a success message but saves nothing). Scorer: `benchmark/score.py`
(keyword-linked, over-counts; the team hand-checks). Numbers are scorer / hand-checked where they differ.

| Dimension | OLD (baseline) | v2 representative (~23 min) | v2 best (~56 min) |
|---|---|---|---|
| Wall-clock | 13.1 min | 22.9 min | 56.2 min |
| Bug recall | 1/22 (5%) | 16/22 scorer, 14 hand | 17/22 scorer, **19 hand** |
| T0 recall (money/auth/delete) | **0/5** | 1/5 hand | **4/5 hand** |
| Routes reached | 5 | 13 | 14 |
| Bugs on an untested route | 10 | 0 | 0 |
| BLOCKED verdicts | **60/67** | 4 | 5 |
| Clean-build false failures | **9% (6/69)** | 1% | ~0% |
| NOT TESTED tasks | — | 163 | **285** |

Reading: the old engine is fast only because it reaches almost nothing — 60 of 67 verdicts are "no evidence
recorded." v2 reaches 13–14 routes, leaves zero bugs on untested routes, cuts clean-build false alarms from 9%
to near zero, and lifts recall from 1 to 14–19 bugs and T0 from 0/5 to 4/5. **v2 wins on recall, coverage,
precision, and trust; the old engine wins only on raw speed and single-run determinism.**

v2's own weak spots show in the same table: at 56 minutes it still leaves 285 tasks NOT TESTED, and its T0 recall
swings 1/5 to 4/5 between runs. Both come from the same root cause (section 3, C1).

## 3. Where v2 lags, and why

Ranked by impact on a sellable product.

**C1 — Model-slot starvation (the biggest one).** All model calls share one global semaphore of 6 in-flight calls
on one API key (`v2/llm.py:32`). The provider sometimes caps lower (a run logged "Limit: 3",
`v2-p1_...log:32`). Result: 275–285 tasks finish as "no tester could finish it," and the long T0 journeys
(order, admin, cancel, logout) are exactly the ones starved — which is why T0 recall is unstable.
Root cause: one key, a hard concurrency ceiling.

**C2 — No safe-write mode.** Writes are all-or-nothing through `--allow-writes`; the guard keys only on HTTP
method + a global bool + a static allowlist (`tools/write_guard.py:120-135`). There is no "create is OK, delete
and edit are blocked," and no cleanup of test data. On a real production site, writes must stay OFF, so a whole
bug class (checkout, create, update) cannot be tested safely. This is the headline product feature, and it is
not built.

**C3 — A latent guard crash.** The two inline route handlers read `request.post_data` without a try/except
(`v2/crawler.py:176`, `v2/tester.py:204`). Playwright raises on non-UTF-8 bodies (binary or multipart uploads).
The canonical guard already guards this (`tools/write_guard.py:152-155`); the two copies do not. It did not fire
on the benchmark (small form posts), but a client site with file uploads would trigger it.

**C4 — Two whole bug classes are unreachable.** Testers share one browser context, so they cannot hold two
sessions at once. Session-invalidation and concurrent-session bugs (for example logout-does-not-end-the-session)
are marked BLOCKED, not tested.

**C5 — T0 recall is the core quality gap.** Best run 4/5, typical run 1/5. Money/auth/delete bugs need long
journeys plus a check of server state *after* the action. The judge's "success trap" rule is half of this; the
other half (re-read the resource after a write) is not yet systematic.

**C6 — No trustworthy automated score.** The scorer links by keyword and over-counts; scorer and hand-checked
numbers differ by up to 5 bugs. The product cannot yet report its own accuracy without a human pass.

**C7 — The coverage feature regresses under the slot cap.** Turning on catalog seeding (`v2/catalog.py`) dropped
the score to 15/22, T0 1/5, because extra tasks starve the deep journeys. The flagship "test any product type"
feature is net-negative until C1 is fixed.

**C8 — No cross-run memory.** `board.db` is deleted at the start of every run. Each run re-crawls and re-plans;
no reuse of a prior passing flow or known-bug map.

**C9 — Not deployable yet.** The job server is standard-library HTTP with no TLS, and the token travels in the
report URL. It must sit behind HTTPS on a VM before any client gets the address.

## 4. Solutions (prioritized, with rough effort)

1. **C1 — second provider key, higher concurrency (M, highest ROI).** Make `V2_MAX_CONCURRENT_CALLS` per-key and
   sum across keys; the code already honors the env var. Interim wins: shorter per-task step budgets, try
   ARIA-only before full HTML, a faster judge model. This single change most improves recall and T0 stability.
2. **C2 — build safe-write mode (M).** Extend the guard to a 3-state policy: allow create-shaped non-GET, block
   DELETE and edits to existing records, record created IDs from 2xx responses, and run a cleanup pass at
   teardown. Pair with the "write ledger" (reject a "created" claim with zero successful writes).
3. **C3 — wrap `post_data` (S).** Copy the try/except already in `write_guard.py:152-155`, or route all three
   call-sites through one shared helper so they cannot drift. Add a regression test.
4. **C5 + C4 — lift T0 (M).** Give journey testers two browser contexts (session A / session B), and add
   post-action server-state assertions (GET the resource after create/delete/logout and compare). Directly
   raises T0 recall, the core differentiator.
5. **C6 — make the score trustworthy (S).** Use the per-bug `oracle` already in `bugs.yaml` for deterministic
   caught/missed, and add a "needs human confirm" column. Needed before any public accuracy claim.
6. **C9 — deploy behind HTTPS (M, mostly ops).** TLS reverse proxy, move report links to short-lived signed
   tokens out of the URL, ship the existing Docker image to the VM.
7. **C8 — cross-run memory (L, later).** One store per site: passing flows (replayable) and a known-bug map.

## 5. Market requirement

**Size and growth.** Automation testing is about USD 40 billion in 2026, growing 14–15% a year; the AI-testing
subset is about USD 9–12 billion, growing 22–27% a year. The category is large, crowded, and still forming.

**The pain we already answer.** The loudest, most repeated complaint about AI testing is **false confidence** —
an agent that reports "pass" while the app is broken. The emerging best practice is to verify against real system
state, not the agent's claim, and to never grade "exists in code but behaviour unverified" as a pass. This is our
core rule ("no proof, no green"). We are aligned with where the market is moving, not chasing it.

**The adjacent pains.** Test creation and maintenance are the top two time costs (about 70% and 60% of teams).
Flaky tests and green builds that hide bugs erode trust. Buyers increasingly want the agent to find real,
reproducible bugs with evidence — not to generate more brittle tests.

**The field.** Autonomous, goal-driven rivals: QA.tech, testRigor, Testsigma Atto, Applitools Autonomous, mabl
agents. Open-source: Autonoma, Explorbot. Managed service: QA Wolf. Most compete on "write and heal tests from
plain language." Few compete on "prove every result and refuse a false green." That is our opening.

**Enterprise entry bar.** SOC 2 Type II (and often ISO 27001), SSO (SAML/OIDC), role-based access, audit trails,
native CI/CD (GitHub Actions / Jenkins), and real parallel execution across many sessions.

**Pricing shapes.** Two models dominate: managed service (QA Wolf, about USD 60k–250k/year) and self-serve,
usage-metered or seat-based (Autify and Octomind from about USD 99/month; mabl and Meticulous quote only).
Self-serve usage pricing fits early-stage buyers' runway.

## 6. Positioning

One line: **"The QA agent that proves every pass — and refuses to show green without evidence."**

Wedge: lead with the proof rule and the T0 catch (money / auth / delete / data-loss bugs that other agents pass).
The deliverable that sells is the **proof report** — a verdict with the exact step and the evidence behind every
bug, and an honest "not tested" list. That report is also the viral artifact (shareable link, PDF).

Beachhead: startups and mid-market teams shipping fast, where a false green is expensive and a managed service is
out of budget. Land self-serve, expand to CI/CD gating.

## 7. Path to market-ready

**Phase 0 — make the core honest (days).** Fix C3 (crash). Make the score trustworthy (C6). Lock one flagship
demo site and one clean proof report.

**Phase 1 — the wedge (2–4 weeks).** C1 (second key, more slots) to kill the NOT-TESTED flood and stabilise T0.
C2 (safe-write) so real sites can be tested without risk. C4+C5 (two sessions, server-state assertions) to push
T0 recall to a reliable 4–5/5. Outcome: "we catch the money/auth/delete bugs others pass, and we prove each one."

**Phase 2 — deployable product (3–6 weeks).** C9 (VM + HTTPS, token out of the URL). A GitHub Action that runs on
each pull request and posts the proven bugs as a check. The mission-control UI (done) plus the proof report as
HTML / PDF. Self-serve sign-up with usage-metered pricing.

**Phase 3 — enterprise and scale (quarter+).** SOC 2 Type II, SSO, role-based access, audit trail. Cross-run
memory (C8). Multi-tenant and parallel scale. Managed-service tier for teams that want it done for them.

## 8. Main risks

- **Provider dependence.** One model key is both the performance ceiling (C1) and a single point of failure.
  A second provider is a reliability need, not only a speed need.
- **Accuracy claims.** Do not publish a recall number until C6 makes the score deterministic. A wrong public
  number is worse than none.
- **Write safety on real sites.** Until C2 ships, keep writes OFF on any production site. One deleted record at a
  client would undo the "trust" positioning.
- **Crowded market.** Many funded rivals. We win only if the proof-first message and the T0 catch are real and
  demonstrable, not slideware.
